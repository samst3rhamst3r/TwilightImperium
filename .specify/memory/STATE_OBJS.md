## Summary

Build the State-object layer: mutable, per-game dataclasses that hold live
gameplay data, structurally parallel to `config/` but never frozen. State
objects must be self-contained (edit/query/derive only from their own
already-known data), serializable to and from a save dictionary with exact
round-trip fidelity, and constructible from scratch via a `new_game()`
classmethod that applies game-rule defaults without external input from the
caller.

## Requirements

- No State object class may be frozen once instantiated, though individual
  fields may be `Final` where conceptually immutable after construction.
- Every State object must be `Serializable` — savable to, and loadable from,
  a save dictionary.
- `src/app/state`'s file/folder structure generally follows `src/app/config`,
  deviating only where State-specific functionality requires it.
- State objects must not hold live instances of other game objects, except
  `GameState` itself — cross-references are by `config_id`/`instance_id`
  string, never a direct object reference.
- State object data holds only simple primitives, simple containers of
  primitives (`tuple`/`MappingProxyType`, never bare `list`/`dict`/`set`), or
  string references to other State objects.
- State methods are scoped to what an object can do to its own internal
  data — edit, query, derive directly from that data. Behavior belonging to
  higher layers is deferred until that layering exists.
- Loading from a save dictionary must recreate an exact replica of the
  object that existed before the save was taken.
- `new_game()` must propagate default construction of State objects
  according to game rules, with no additional input required from the
  calling entity.

## Out of Scope

State objects must not hold direct references to Config-layer dataclass
objects — Config resolution happens at the Resolved layer (see
[RESOLVED.md](RESOLVED.md)), not here.

## Technical Context

**Language/Version**: Python 3.14 (per active `.venv`; no pinned
`requires-python` in `pyproject.toml` yet)

**Primary Dependencies**: Standard library only — `state/` does not import
PyYAML or any config-loading dependency directly

**Storage**: Plain-dict save format (`Serializable.save()` /
`init_from_save()` round-trip); no database — see ARCHITECTURE.md §3
"Serializable — single shared terminal / ABC root"

**Testing**: pytest (`pytest==9.1.1` per `requirements.txt`), mirroring
`src/app/state/**` under `tests/test_state/**` one-for-one per CLAUDE.md
Test layout convention

**Target Platform**: Cross-platform Python library (no OS-specific
behavior in this layer)

**Project Type**: Single project — internal architectural layer, not a
standalone service/app

**Performance Goals**: Not specified; no dedicated performance target has
been set for this layer

**Constraints**: `slots=True` and `frozen=True` are both deliberately not
used on State dataclasses (ARCHITECTURE.md §3 — multiple-inheritance
mixin slot conflicts, and incompatibility with the `load()`
`__new__`-bypass pattern, respectively); every new State-to-State
relationship must be classified per ARCHITECTURE.md §6 before adding a field

**Scale/Scope**: Full per-game State model — `GameState`, `PlayerState`,
`PlanetState`, `SystemState`, `SpecialTokenStates`, the `unit/` package
(`UnitState`, unit location), and the `card/` package (action, agenda,
deck, objective, promissory note, strategy, tech cards), plus the shared
`base/` mixins (`Serializable`, `Exhaustible`/`ExhaustableStateMixin`,
ownable, other mixins)

## Open Questions

- Is `Final` on frozen-after-construction dataclass attributes the right
  mechanism? Some fields don't change after object creation, but their
  dataclass can't use `frozen=True` because other fields need mutation.
  `Final` only helps static type-checkers, not runtime enforcement — a more
  robust mechanism may be needed. (See also ARCHITECTURE.md §3's `Final`
  guidance for `SystemState.map_hex_coordinate` etc. — that guidance
  currently accepts this as a static/convention-level contract, not a
  dataclass-enforced one.)
- **Secret objective scored-ownership**: should
  `SecretObjectiveCardState.owner_player_id` be retained permanently once
  set (per ARCHITECTURE.md §6's worked example), or released on scoring
  (current code's `release_owner_and_score`)? A game effect converts a
  scored secret objective into a publicly-scoreable one, at which point
  per-player ownership becomes meaningless — weighed against the ~99%
  common-case states (in hand, scored, or in deck). Unresolved; current code
  releases ownership on score, relying on
  `PlayerState.scored_objective_card_ids` as the sole record of who scored
  it.
- **Agenda/Tech card population strategy**:
  `GameState.agenda_cards`/`tech_cards`
  (`MappingProxyType[str, AgendaCardState | TechCardState]`, holding only
  the mutable `exhausted` state a subset of cards can have) — populated
  *sparsely* (only cards ever exhausted) or *densely* (one entry per
  `config_id` from game start)? Related: unlike Tech (never drawn), Agenda
  cards are physically drawn from a real deck each Agenda phase — whether
  `agenda_cards` needs `CardDeckState`-style deck/discard semantics instead
  of (or alongside) a flat `MappingProxyType` is the same unresolved shape
  question. This reverses half of an earlier decision (commit `c875fcb`,
  "a tech card has no state at all") — that commit's *ownership* conclusion
  (`PlayerState.researched_tech_ids`, many:many) remains correct; only its
  "no state at all" claim is reversed here, given real per-card exhaustion
  effects that commit didn't account for. Leave unresolved until
  `new_game()` design settles it.
