## Summary

Build the "Resolved" layer: the integration layer above the disparate
`config/` and `state/` layers. A `Resolved*` object is a thin, per-operation
binding of one live State object + its resolved Config
(`BaseResolvedObj[TState, TConfig]`, `state` + `config` fields), generally —
but not always — composed of same-type Config/State pairs (e.g.
`ResolvedUnit` from `UnitConfig` + `UnitState`); some are legitimately
heterogeneous (e.g. Faction Config + Player State, since `PlayerState`
references a static Faction definition). This layer exists to give the
Domain Service layer (not yet built) a single, Config-aware place to call
for per-entity queries/decisions, so Services never manipulate raw
Config/State objects directly.

## Requirements

- Every "leaf" Config/State class pairing is reviewed to determine its
  eligibility for a `Resolved*` combination — not every Config/State pair
  needs one (see ARCHITECTURE.md §4: build only once 2+ real methods
  genuinely need State+Config together).
- `Resolved*` classes are built as functional aggregations of one Config +
  one State object, via the generic `Resolved[TState, TConfig]` base for the
  common case; entities needing multiple Configs (or none) use a bespoke
  dataclass instead of forcing the generic shape.
- The (future) Domain Service layer will call `get_resolved_item`-style
  factory methods to construct `Resolved*` objects on demand for the actions
  it requests — Services never access Config/State objects directly.
- Tests must comprehensively cover every `Resolved*` class's capabilities.

## Out of Scope

Domain Services themselves (`MovementService`, `CombatService`, etc.) that
the Orchestrator will call are **not** covered by this plan. If a capability
requires complex resolution across State objects of heterogeneous type
(e.g. `UnitState` + `SystemState` together), that reasoning belongs to the
Services layer (ARCHITECTURE.md §5), not to a `Resolved*` class.

## Technical Context

**Language/Version**: Python 3.14 (per active `.venv`; no pinned
`requires-python` in `pyproject.toml` yet)

**Primary Dependencies**: Standard library only for this layer — no new
third-party dependency required (PyYAML is a `config/`-layer loader
dependency, not used directly by `resolved/`)

**Storage**: N/A — `Resolved*` objects are never persisted (ARCHITECTURE.md
§4: constructed on demand, threaded through one operation's call chain,
never cached/stored on `GameState`)

**Testing**: pytest (`pytest==9.1.1` per `requirements.txt`), mirroring
`src/app/resolved/**` under `tests/test_resolved/**` per this project's
test-layout convention

**Target Platform**: Cross-platform Python library (no OS-specific
behavior in this layer)

**Project Type**: Single project — internal architectural layer, not a
standalone service/app

**Performance Goals**: Not specified; re-resolving a `Resolved*` object is
explicitly treated as O(1)-lookup-cheap (ARCHITECTURE.md §4), so no
dedicated performance target has been set for this layer

**Constraints**: One-way layering (`resolved` depends on `config` + `state`
only, never the reverse); `Resolved*` objects MUST NOT mutate Config, only
reference it; MUST NOT be cached/stored on `GameState`

**Scale/Scope**: Currently 6 concrete `Resolved*` classes exist
(`ResolvedActionCard`, `ResolvedPlanet`, `ResolvedPlayer`,
`ResolvedPromissoryNote`, `ResolvedStrategyCard`, `ResolvedUnit`) plus the
shared `BaseResolvedObj` generic base and `shared/protocols.py` trait
Protocols — scope grows incrementally as new leaf classes justify a
`Resolved*` per ARCHITECTURE.md §4's "2+ real methods" rule

## Open Questions

- How should the Domain Service layer "request" a particular `Resolved*`
  object — a single generic `get_resolved_item(...)` dispatcher, or
  per-entity factory methods (`GameState.resolved_unit(unit_id)`, etc.)?
  ARCHITECTURE.md §1 states `GameState.resolved_*()` factory methods are the
  only sanctioned access point, but the exact call signature/dispatch
  mechanism is not yet finalized.
- How ephemeral should this layer be in practice — strictly
  constructed-and-discarded within one calling method (as ARCHITECTURE.md §4
  mandates), or is there a legitimate case for passing a `Resolved*` object
  down through a short call chain within a single Service operation? (§4
  already answers "thread through the operation's call chain" — this
  question is really about how deep that chain is allowed to go before
  re-resolving instead of passing down.)
- Should there be a single `resolved_loader.py`-style module (mirroring
  `config/yaml_loader.py`) that centralizes "State + Config → Resolved*"
  construction, or should each `Resolved*` class's construction stay
  distributed as classmethods/factory functions per class?
